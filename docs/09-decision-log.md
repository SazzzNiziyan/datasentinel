| D-22 | API scaffold and health endpoints                                    | NestJS 12 on Express, ESM. `GET /health/live` always returns `{"status":"ok"}`; `GET /health/ready` runs the database (`pg`, `SELECT 1`), Redis (`ioredis` PING), and storage (S3 `HeadBucket` on the uploads bucket) checks in parallel with a 2 s timeout each and returns 200 `ready` or 503 `not_ready` with only `up`/`down` per dependency (no URLs, errors, or topology). | D-23 | Request IDs and structured logs                                      | `nestjs-pino` writes one JSON line per request (pino; stdout). Every response carries `x-request-id`: a caller's value is reused only if it matches `[A-Za-z0-9._:-]{1,128}`, otherwise a UUID is generated; the same ID is the log's `req.id`. Request logs keep only ID, method, path (query string dropped), status, and timing; headers are never logged (cookies, tokens, OAuth codes). Fields named password/secret/token/accessToken/refreshToken/apiKey/authorization/cookie/connectionString are censored up to two levels deep as a second line of defense. Error messages and stacks pass through `scrubSecrets`, which removes credentials from URLs (`scheme://user:pass@` becomes `scheme://[redacted]@`); startup crashes are scrubbed the same way. Log level from `LOG_LEVEL`. `AppModule.register({ logLevel, logStream })` lets tests silence or capture logs. Workspace/user IDs join the log context with sign-in (Phase E).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | Decided | 2026-10-17 |
| D-24 | Worker entry point and queue wiring                                  | `apps/worker` is a NestJS application context (no HTTP) built like the API (D-22 configs, env files, scripts). Queues use plain `bullmq` 6 in one Nest service (`SystemQueueService`) rather than `@nestjs/bullmq`, to avoid another wrapper that must track Nest 12; the BullMQ worker gets its own `ioredis` connection with `maxRetriesPerRequest: null` and closes on shutdown so a running job can finish. Queue and job names plus job data types live in `packages/contracts` (`SYSTEM_QUEUE` "system", `PING_JOB` "ping"); job data holds IDs and safe values only. The worker logs job ID and name, never job data. Sample job: `ping` returns `{ pong: true, sentAt }`; `pnpm --filter @datasentinel/worker sample-job` (after `build`, with the worker running) adds one and prints the answer. The Redis round-trip test runs when local Redis answers and is skipped otherwise. `msgpackr-extract` (optional native speed-up) is denied install scripts via `allowBuilds` in `pnpm-workspace.yaml`.                                                                                                                                                                                                                                                                                                                                                                                                                                                            | Decided | 2026-10-17 |
